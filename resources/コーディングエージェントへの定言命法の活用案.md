# コーディングエージェントへの定言命法の活用案

## はじめに

コーディングエージェントには、与えられた目的を達成する能力だけでなく、その目的をどのような方法で達成するかを判断する能力が必要です。

たとえば、「テストを通してください」という依頼に対して、実装を修正することも、失敗しているテストを削除することも、表面的には同じ目的を達成できます。しかし、この二つは開発上の意味がまったく異なります。

一般的なルールベースのエージェントでは、「テストを削除してはいけない」「lint を無効化してはいけない」といった禁止事項を個別に追加して対処します。しかし、開発中に起こり得るすべての問題を事前に列挙することは困難です。

そこで、個々の禁止事項よりも上位の判断原則として、定言命法の考え方を利用できます。

ここで扱う定言命法は、カント哲学をそのままソフトウェア開発へ適用するものではありません。コーディングエージェントの判断に利用できるように、次の問いへ単純化して扱います。

> この行動を、同じ条件にあるすべての場合で認めても、開発の仕組みは成立するでしょうか。

この問いによって、エージェントが「今回だけなら都合がよい」という理由で、不適切な方法を選ぶことを防ぎます。

---

## 目的を達成することと、正しい方法を選ぶことは別です

コーディングエージェントは通常、何らかの目的を与えられて動きます。

たとえば、次のような目的があります。

- ビルドを成功させる
- テストを通す
- Issue を完了する
- API を追加する
- Flutter の実装を C# へ移植する

このような「目的を達成したいなら、この行動をする」という考え方は、仮言命法として表現できます。

たとえば、

> テストを通したいなら、失敗しているテストを無効化する。

という判断も、目的と手段だけを見れば成立しています。

しかし、これを一般的なルールへ変換すると問題が見えてきます。

> テストが失敗した場合、そのテストを無効化してよい。

このルールをすべての開発者やエージェントが採用すると、テストは不具合を検出する仕組みとして機能しなくなります。

一方で、

> テストが失敗し、実装が仕様を満たしていない場合、実装を修正する。

というルールであれば、同じ条件にあるすべての場合へ適用してもテストの仕組みは維持されます。

この違いを判定することが、定言命法を利用する目的です。

---

## 仮言命法を定言命法へ変換します

エージェントが考えた行動は、まず目的を含む形で表現できます。

> X を実現したいなら、Y をする。

これを、その場の目的から切り離して一般化します。

> 条件 C のとき、Y をしてよい。

そのうえで、この規則を同じ条件にあるすべての場合へ適用した結果を考えます。

たとえば、次の判断があります。

> ビルドを成功させたいなら、警告をエラーとして扱う設定を削除する。

これを一般化すると、

> 厳しい品質チェックによってビルドが失敗した場合、その品質チェックを無効化してよい。

となります。

この規則を一般化すると、品質チェックは失敗したときほど無効化されることになります。そのため、品質チェックを導入する意味そのものが失われます。

このような規則は採用しません。

反対に、

> ビルドが失敗し、その原因が実装上の誤りである場合、実装を修正する。

という規則であれば、一般化してもビルドや品質保証の仕組みは維持されます。

このように、エージェントが提案した行動を一度一般則へ変換することで、目の前の目的だけに引きずられた判断を減らせます。

---

## 自律実行できる行動と、人間へ確認する行動を分けられます

すべての行動を定言命法として一般化できるわけではありません。

実際のソフトウェア開発には、一時的な制約や外部ライブラリの不具合があります。その場合、一般的には望ましくない対応を、今回だけ行うことがあります。

たとえば、利用しているライブラリに既知の不具合があり、その修正を待てない場合、一時的な回避コードを追加することがあります。

このような判断を、

> 問題が発生したら常に回避コードを追加する。

という一般則にはできません。

しかし、

> このライブラリのこの不具合が修正されるまで、この場所だけ回避コードを利用する。

という局所的な例外なら合理的な場合があります。

そのため、エージェントの判断結果は二値ではなく、少なくとも三つに分ける必要があります。

- Adopt: 一般則として採用できる
- Local-only: 今回の条件では利用できるが一般則にはできない
- Reject: 局所的にも採用すべきではない

`Adopt` の行動はエージェントが自律実行できます。

`Local-only` の行動は、エージェント自身で例外を決定せず、ユーザーへ許可を求めます。

`Reject` の行動は、ユーザーへ通常の確認を求める対象にもせず、別の方法を探します。

この区別によって、「ユーザーが許可すれば何でもできる」という状態を防げます。

## ユーザーは例外を承認する役割を持ちます

この考え方では、ユーザーへの質問も変わります。

一般的なコーディングエージェントは、

> この場合はどうしますか。

という自由回答の質問をすることがあります。

しかし、この質問では設計作業そのものをユーザーへ戻してしまっています。

定言命法を利用する場合は、エージェント側で判断可能な形まで問題を整理してから質問します。

たとえば、次のように提示できます。

> 今回のみ生成コードを直接修正する例外を認めますか。

その際には、例外の内容だけでなく、理由や範囲も明示します。

- 対象: Issue #123 の一つのファイルのみ
- 理由: generator 側の修正は今回の Issue の対象外
- 影響: 再生成すると変更が失われる
- 代替案: generator を修正する

ユーザーは `Approve`、`Reject`、`Revise` のような選択肢で答えます。

`Revise` が必要なのは、エージェントが問題の捉え方そのものを間違えている可能性があるためです。

たとえば、エージェントが「互換性を維持するか、破壊するか」の二択を提示しても、実際には「新しい API を別名で追加する」という第三の選択肢が存在することがあります。

そのため、ユーザーへの質問は可能な限りクローズドクエスチョンにしつつ、エージェントが作った前提を修正できる経路を残します。

## AGENTS.md に何を書くべきかを判断できます

同じ考え方は、AGENTS.md に記載するルールの選定にも利用できます。

AGENTS.md は、一つの Issue のための作業メモではありません。そのスコープで繰り返し適用する開発上の原則を書く場所として扱えます。

そのため、AGENTS.md に追加するルールについても、

> このルールを、このスコープの同種作業すべてへ適用してもよいでしょうか。

と考えます。

たとえば、

> 公開された振る舞いを変更した場合、その振る舞いを検証するテストを追加または更新する。

というルールは、リポジトリ全体へ適用できます。

一方、

> Issue #312 では PNG 比較テストを利用する。

というルールは、特定の Issue にしか必要ありません。

このような情報は Issue や作業計画へ置くべきであり、AGENTS.md には置きません。

また、一般化できるからといって、すべてのルールを AGENTS.md に追加する必要もありません。

たとえば、

> 変数には意味のある名前を付ける。

というルールも一般化できますが、多くのコーディングエージェントがすでに理解している内容であれば、毎回コンテキストへ含める価値は小さくなります。

AGENTS.md に残す価値が高いのは、次のような原則です。

- 同じスコープの作業へ継続的に適用する
- プロジェクト固有の判断を含む
- エージェントが間違える可能性がある
- 違反した場合の修正コストが高い
- 特定の Issue や一時的な事情に依存しない

この考え方を利用すると、AGENTS.md が一時的な作業指示で増え続けることも防ぎやすくなります。

## テストを書くべきかの判断にも利用できます

テストの必要性も、単純な規則だけでは判断しにくい問題です。

「コードを変更したら必ずテストを書く」というルールでは、コメント修正や内部リファクタリングにまで不要なテストを要求する可能性があります。

反対に、「既存テストが通れば新しいテストは不要」というルールでは、新しく追加された仕様が検証されない場合があります。

ここでも一般化による判断が利用できます。

> この種類の変更が、今後すべてテストなしで行われても、システムの正しさを継続して確認できるでしょうか。

たとえば、新しい公開 API の振る舞いを追加した場合を考えます。

> 公開 API に新しい振る舞いを追加しても、テストを追加しなくてよい。

これを一般化すると、公開 API の仕様が増えても自動的な検証が増えません。そのため、時間が経つほど仕様とテストの対応が失われます。

一方で、コメントの誤字修正について、

> コメントだけを修正した場合、新しいテストを追加しなくてよい。

という規則は、一般化してもシステムの動作保証には影響しません。

この方法では、変更したコードの量ではなく、新しく保証すべき契約が生じたかどうかを中心に判断できます。

また、テストが必要だと判断した後に、どのレベルのテストを書くかは別の問題として扱います。

公開された振る舞いを保証したい場合、private メソッドへ直接テストを書く必要はありません。利用者から観測できる安定した境界で検証する方が、内部実装の変更に強いテストになります。

定言命法は「テストを必要とするか」の判断に利用し、具体的なテスト境界は設計上の別の原則で判断します。

## サブエージェントとして分離できます

この判断をメインのコーディングエージェント自身にすべて行わせる必要はありません。

専用のサブエージェントとして分離できます。

たとえば `MaximReviewer` のような役割を持つエージェントを用意します。

メインエージェントは、

> ビルドを通すため、失敗している検証を無効にしたい。

という仮言命法を提出します。

MaximReviewer は、これを一般則へ変換します。

> 検証に失敗した場合、その検証を無効にしてよい。

その後、一般化した場合の問題を検査し、`Adopt`、`Local-only`、`Reject` のいずれかを返します。

このサブエージェントの責務は、最適な設計を選ぶことではありません。

たとえば、「Repository Pattern を使うべきか」「DbContext を直接使うべきか」といった設計判断は、どちらも一般則として成立する可能性があります。

定言命法による審査が判断するのは、

> その方法を一般的な行動原則として認めてもよいか。

という点です。

設計上の優劣は、変更容易性、責務分割、依存関係、実装コストなどの別の基準で評価します。

## 反例を探すエージェントも必要です

一般則を作るエージェントだけでは不十分です。

エージェント自身が、自分に都合のよい表現へ規則を書き換える可能性があるためです。

たとえば、

> テストを通すため、失敗したテストを削除する。

という行動を、

> 間違っているテストは削除してよい。

と書き換えれば、一見もっともらしく見えます。

しかし、本当にそのテストが間違っているかどうかは別途確認する必要があります。

そのため、一般化された規則に対して反例を探す役割を分離する方が安全です。

構成としては、次のようになります。

- Agent: 行動候補を生成する
- Maxim Generator: 行動を一般則へ変換する
- Universalization Verifier: 一般則として成立するか判断する
- Counterexample Generator: その規則が破綻する具体例を探す
- Executor: 承認された行動だけを実行する

同じモデルをすべての役割で利用することもできますが、論理的には役割を分離しておく方が検証しやすくなります。

## Lean による形式検証へつなげられます

定言命法を一般則として表現できるようになると、一部の規則は形式的な命題へ変換できます。

ただし、Lean が「その行動は道徳的に正しい」と証明するわけではありません。

Lean で証明できるのは、こちらが定義した状態や不変条件について、

> この規則を適用しても、必要な性質が維持される。

ということです。

たとえば、リポジトリの状態について次の不変条件を定義したとします。

> 公開仕様として定義された振る舞いには、対応する検証が存在する。

ある行動規則をすべての該当状態へ適用しても、この不変条件が維持されることを Lean で証明できれば、その規則には機械的な根拠を与えられます。

反対に、具体的な反例を構築できれば、その一般則が成立しないことを示せます。

考え方としては次の変換になります。

自然言語による行動案  
→ 一般化された規則  
→ 状態と遷移  
→ 維持すべき不変条件  
→ Lean の命題  
→ 証明または反例

ただし、すべての設計原則をこの方法で証明できるわけではありません。

「読みやすいコードを書く」「自然な API にする」といった判断は、そのままでは数学的な命題になりません。

一方で、

- 依存方向を守る
- 公開契約を維持する
- 仕様変更なしに公開動作を変えない
- 必要な検証を削除しない

といった規則は、状態や依存グラフを定義できれば形式化しやすくなります。

## 強化学習の報酬として利用できます

この仕組みは、コーディングエージェントの強化学習にも利用できます。

一般的な強化学習で「テストが通ったら高い報酬」を与えるだけでは、エージェントが不適切な方法でテストを通す可能性があります。

たとえば、次の行動はすべて「テスト成功」という結果を作る可能性があります。

- 実装を正しく修正する
- テストを削除する
- assertion を弱くする
- エラーを握りつぶす
- CI の検証を無効化する

結果だけを評価すると、この違いを学習できません。

そこで、タスク達成の報酬とは別に、行動原則に対する報酬を与えます。

`Adopt` できる行動には正の報酬を与え、`Reject` される行動には負の報酬を与えます。

`Local-only` は、状況によって必要になる行動なので、中立的な扱いにできます。

この方法では、

> 問題を解決できたか。

だけでなく、

> 再利用可能な適切な行動原則に従って問題を解決したか。

も学習できます。

また、一つの問題に対して複数の行動候補を生成し、その一般化可能性を比較すれば、Preference Learning 用のデータも作れます。

たとえば、

- 実装を修正する
- テストを削除する
- assertion を弱める
- 仕様変更に合わせてテストを更新する

という候補について、一般化可能性を評価すれば、どの行動を優先すべきかという比較データを作れます。

---

## 定言命法だけでは設計は決められません

この方式には明確な限界があります。

定言命法による判断は、ある行動を一般則として認められるかどうかを評価することには向いています。

しかし、複数の妥当な設計から最も適切なものを選ぶことには向いていません。

たとえば、

> 外部サービスへのアクセスを Interface で抽象化する。

という規則も、

> 現在一つしか実装がないため、具体クラスを直接利用する。

という規則も、条件を適切に設定すれば一般化できます。

どちらを選ぶべきかは、将来の変更可能性、テスト方法、公開 API、実装コストなどを考えて判断する必要があります。

そのため、定言命法は設計原則の代わりではなく、設計判断の後に置く行動審査として扱う方が適しています。

概念的には次の順序になります。

目的  
→ 制約  
→ 設計原則  
→ 行動候補  
→ 一般化可能性の審査  
→ 必要ならユーザーによる例外承認  
→ 実行

この構造では、設計原則が「何をするか」を決め、定言命法による審査が「その方法を許してよいか」を確認します。

## ユーザーとエージェントの役割も整理できます

この仕組みを導入すると、コーディングエージェントとユーザーの役割も明確になります。

エージェントは、既存の原則から判断できる範囲では自律的に動きます。

一般則として扱えない判断が必要になった場合は、勝手に例外を作らず、ユーザーへ例外の承認を求めます。

ユーザーは毎回実装方法を考える必要はなく、

> この条件では、通常の原則に対する例外を認めるか。

を判断します。

つまり、ユーザーが細かな操作を指示し、エージェントがその通りに動く関係から、

> エージェントが原則に従って自律的に作業し、人間が原則そのものや例外を管理する。

という関係へ変えられます。

これは、コーディングエージェントへより大きな自律性を与えながら、勝手な判断を増やさないための一つの方法です。

---

## まとめ

コーディングエージェントへの定言命法の利用は、個別の禁止事項を大量に教える代わりに、行動を一般化して審査する仕組みとして利用できます。

中心となる考え方は、

> この行動を、同じ条件にあるすべての場合で認めても、開発の仕組みは成立するでしょうか。

という問いです。

この考え方を利用すると、テストを削除して成功扱いにする、一時的な都合を恒久的な設計へ残す、自分の作業だけを例外扱いするといった行動を、個別の禁止事項なしでも検出できる可能性があります。

また、一般化できないからといって、すべての行動を禁止する必要はありません。局所的には合理的な行動を `Local-only` として分類し、人間が例外として承認できるようにします。

この仕組みは、AGENTS.md に書く原則の選定、テストの必要性判断、ユーザーへの質問、サブエージェントによる行動監査、Lean による形式検証、強化学習の報酬設計まで同じ考え方でつなげられます。

最終的には、定言命法を哲学的な標語として使うのではなく、

> **エージェントが提案した局所的な行動を、再利用可能な一般則へ変換し、その一般則がシステムの不変条件を壊さないか確認する仕組み**

として扱うのが、この案の中心になります。
